## Method and measurement boundaries

The dedicated local diagnostic uses the unchanged image and automatic HEALTHCHECK.
Empty provider keys, no volume, host 127.0.0.1:8082 to container 10000,
HOSTNAME=0.0.0.0, 512 MiB, 0.1 CPU and the existing 384-MiB V8 heap setting.
Direct requests have an absolute five-second deadline, new connections and the
synthetic configured Host. The HTTP client/collector runs outside the constrained
container; application and probes share its budget. Heavy lint/build/tests were
delayed until measurements finished. Ambient laptop/VM load is uncontrolled;
unrelated software was preserved.

Docker health logs are collected every two seconds beyond the last-five ring.
All 15 unique completed entries were captured without a collector error. The
dedicated diagnostic took 284945.922 ms including setup, manual traces and cleanup.
Selected PID 1 status and cgroup files are sampled at readiness, after 50 steady
requests and at the end. Collector/sample overhead is small but nonzero. Steady
requests have one-second pauses; after manual tracing twenty more use that cadence.
Automatic probes remain enabled throughout.

Listening is observed from Docker-timestamped Next Network output. In installed
Next 16.4.6 it is emitted from the listening callback **before config/handler
initialization**. It is a callback-log observation, not a kernel bind timestamp.
Docker's published TCP port can accept connections before Node binds. The displayed
Ready-in-0ms banner is not used as application readiness.

A test-only wrapper imports the unchanged health script in three fresh Node
processes and records fetch setup, abort/error and resource usage. These manual
executions are not Docker HEALTHCHECK invocations: they finish under the script's
unchanged three-second abort so the stage of failure is observable. Automatic
five-second checks are never disabled or extended. A Node-only trace is the
control. CLI elapsed times include Docker exec overhead; instrumentation adds
some code/IO overhead.

Complete local evidence: `.tmp/render-health/baseline.json` (ignored). Essential

## Exact failure cause

All three traced probes show fetch-enter, fetch-return, signal-abort,
fetch-error-TimeoutError and module-end, with no response-headers/body event.
The bracket around the synchronous first fetch call takes **8.004–12.201 seconds** under the
quota. Node initializes its client on first use in each fresh process. The abort
callback cannot execute while that work occupies the event loop; it runs once
the call returns. The script then sets exit code 1. This repeated cold setup is
not shared with the warm Next process.

Traced probes use 940.868–1105.554 ms of process CPU. At 0.1 CPU this exceeds the
CPU allowance available in five wall seconds, even before competing work and
exec overhead. The Node-only diagnostic control takes 5520 ms end to end. This
identifies a fresh-process/client bootstrap budget mismatch, not a warm endpoint
requiring five seconds, a Gemini/Sarvam wait or memory exhaustion.

Docker reports ExitCode -1 and a five-second execution timeout for every automatic
probe. Its recorded Start/End spans are 6506–17082 ms. Those spans include the
Docker execution lifecycle and are not endpoint response time; extra
launch/termination/accounting delay is observed but not independently decomposed
inside the daemon. Manual Node exit code 1 and Docker-reported -1 are distinct.

## Endpoint and Render comparison

The health GET is synchronous: cached config parsing, provider **configuration
booleans**, in-memory session count, schema validation and JSON response. It does
not construct the provider runtime, call/wait for Gemini/Sarvam, warm greetings,
read the ledger or load seller data. Configured keys do not make it infer.
Verbose-health bearer protection is unchanged. A regression test additionally
sets fake configured flags, replaces fetch with a throwing spy and asserts no call.

Render documents HTTP 2xx/3xx within five seconds and up to 15 minutes for a new
deploy to become ready. Here first 200 occurred 131.635 seconds after start-command
begin, and all 70 later samples were below 596 ms. These measured application
behaviors satisfy the published bounds locally.
[Render health checks](https://render.com/docs/health-checks).

Render's documented readiness check sends HTTP to an existing application; Docker's
command launches another process inside its quota. Their cost/budget boundaries
differ. The official Docker page does not establish whether every internal Docker
HEALTHCHECK detail is honored or ignored by Render; this report assumes neither.
[Docker on Render](https://render.com/docs/docker). Direct HTTP passed even while
the unchanged automatic Docker probes failed.

**No production correction is required for this measured external HTTP contract.**
The five-second fresh-Node/fetch probe remains unsuitable for this local quota.
It was not removed, disabled or given a longer deadline to obtain GO. Making that
separate Docker signal healthy would require a separately validated probe-cost
change; it is not silently treated as fixed here.
